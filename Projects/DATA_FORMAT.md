# 数据格式与迁移设计

最后更新：2026-10-02

## 已确认要求

**当前实现入口（2026-10-02）**：`../app/DATA_FORMAT.md`、`../app/backup.schema.json`、`../app/example-backup.json`。以下保留前期草案；当前采用 workouts 内嵌有序动作／逐组数据，与草案中的独立 workout_exercises / sets 表不同。完整 JSON 覆盖所有模块，CSV 当前只导出运动逐组明细。恢复流程为校验 → 预览 → 明确替换，不合并。实际字段以随 App 导出的说明为准。

- 数据本机保存，无需登录，支持导出与导入备份。
- 用户计划使用约一年，之后可能迁移到其他 App。
- 必须提供定义清楚的数据模板与说明，支持理解和转换历史数据。
- 目标 App 尚未指定；能导出可转换的数据不等于任意第三方 App 都能直接导入。

## 建议方案（设计草案，尚未实现或逐项确认）

提供两种导出：

1. 完整 JSON 备份：用于本 App 恢复和编写迁移工具，保留关联、逐组记录与模板。
2. UTF-8 CSV 数据表：便于在表格软件中查看、处理和转成其他 App 所需格式。按运动记录、动作、训练动作、逐组记录和模板分别导出，通过 ID 关联，不能只导出汇总。

每次导出随附格式说明，包含版本、字段含义、单位、枚举、空值规则、关联关系及示例。备份格式独立于内部数据库实现。

## 建议的数据结构

JSON 顶层包含以下字段；正式实现前提供对应的机器可校验 Schema 与不含真实个人数据的完整示例。

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 格式版本，建议首版为 `1.0.0` |
| `exported_at` | 导出时间，包含时区偏移的时间戳 |
| `app_version` | 生成备份的应用版本 |
| `workouts` | 运动记录列表，含完成和未完成状态 |
| `exercises` | 被引用的内置动作及自定义动作定义 |
| `workout_exercises` | 每次力量训练中的动作实例与顺序 |
| `sets` | 每个动作实例下的逐组实际记录 |
| `templates` | 用户保存的训练模板及有序动作、目标组数和次数 |
| `settings` | 单位、休息时长等可恢复设置 |

### 运动记录 `workouts`

| 字段 | 含义与建议规则 |
| --- | --- |
| `id` | 稳定且唯一的记录 ID，导出和恢复时不重新生成 |
| `sport` | `strength`、`running`、`cycling`、`basketball` |
| `status` | `in_progress` 或 `completed`；草稿不计入已完成运动统计 |
| `local_date` | 运动所属本地日期，`YYYY-MM-DD`，用于日历与周统计 |
| `time_zone` | 记录时的时区标识，避免换时区导致日期统计改变 |
| `started_at` / `ended_at` | 带日期及 UTC 偏移的起止时间；只有时长的补记允许为空，不虚构时刻 |
| `duration_seconds` | 总时长，单位秒；完成记录应为正数 |
| `duration_source` | `timer`、`manual` 或 `time_range`，区分计算来源 |
| `distance_meters` | 跑步／骑行距离，单位米；其他运动为空 |
| `notes` | 可选备注；篮球不提供此输入，值为空 |
| `template_id` | 可选的来源模板 ID；不以当前模板内容替代实际历史记录 |
| `created_at` / `updated_at` | 创建与最后修改时间，区别于实际运动时间 |

篮球的起止时间包含日期以表达跨午夜的运动，时长由两者之差计算。此为存储表达，不增加篮球训练类型等输入。

配速和均速由距离与时长计算，原始距离与时长必须保留；零距离或缺失值不产生无效结果。总时长是否扣除暂停，以及跨天统计口径仍需确定。

### 动作与逐组记录

- `exercises`：稳定 `id`、名称、内置／自定义来源、器械及记录类型；示意素材用资源标识引用，附素材来源信息。
- `workout_exercises`：稳定 `id`、`workout_id`、`exercise_id`、动作顺序及当时动作名称快照。相同动作在一次训练中可出现多次。
- `sets`：稳定 `id`、`workout_exercise_id`、组序号、实际 `reps`、`weight_kg`、`weight_basis` 与完成状态。
- `weight_basis` 明确重量口径，例如杠铃总重、单只哑铃、自重或辅助重量；具体选项待收敛，不能仅靠动作名字猜测。
- 未录入值为 `null`，不能用 0 代替；模板目标次数与实际完成次数分开保存，未完成组不算完成量。
- 删除或修改动作／模板不得使既有训练失去含义；保留历史快照及必要引用，不能级联删除历史训练。
- 若后续允许自定义图片，完整备份需包含本地素材或明确列出缺失项，不能只留下失效的本机 URL。

### 模板 `templates`

保留稳定 ID、名称、创建／修改时间，以及有序动作列表。每个动作条目包含动作 ID、名称快照、目标组数与目标次数；具体是否支持每组不同目标后续收敛。模板改动不回写既有训练。

## 版本、导入与备份流程建议

- 格式版本独立于应用版本；字段或含义变化时升级版本，并提供旧备份迁移规则。
- JSON 用 `null` 表示无值，CSV 使用空单元格；CSV 用同名字段与相同单位，正确处理逗号、换行及中文。面向表格软件的公式字符转义需可逆并写入说明。
- 导入前验证版本、字段、重复 ID、关联完整性和合理数值；不支持的未来版本或异常文件应给出原因，不静默丢弃数据。
- 导入前展示记录数量、日期范围与冲突。合并／覆盖规则尚待确定，执行前应能保存现有数据备份。
- 本机保存不是独立备份；建议提供应用内定期备份提醒，由用户把文件保存到手机“文件”、网盘或电脑。
- 首版备份提醒频率及是否记录“最近导出时间”待定；触发下载不等于已验证用户在外部保存成功。

## 后续实现验收标准

以下为拟定的必要验证，不表示已完成测试：

- 使用覆盖一年跨度、四类运动、逐组明细、模板和自定义动作的模拟数据，导出后在空白环境恢复，比较原始字段、数量与关联关系。
- 覆盖中文、标点、换行、未录入重量、跨午夜、时长补记及重复导入场景。
- 仅凭导出文件和格式说明，能够还原一次力量训练的动作顺序、每组重量与次数，以及其他运动的日期、距离和时长。
- 应用后续升级不能使已有备份无法恢复；格式变更需要迁移验证。

## 新增模块的数据扩展草案

放纵餐与精灵养成已加入需求，建议完整备份新增以下内容；计分边界尚待澄清，暂不冻结正式 Schema。

- `meal_records`：每次放纵餐的稳定 ID、实际发生日期／时间、创建与修改时间；具体用户输入字段待设计。
- `scoring_rules`：规则版本、初始分数、计分启用日期、周界限与时区、达标条件、连续规则和分数下限。
- `score_summary`：独立总分的初始值（60）与当前值；仅用于历史统计，可由周流水核对，不用各精灵分之和替代。
- `weekly_scores`：稳定周标识、周次数、确认／结算状态、连续周数、规则变化值、规则版本、总分结算前后值与实际变化、结算时装配精灵 ID、该精灵结算前后值与实际变化。两类分数分别以 0 为下限，实际变化可能不同；历史归属不能取恢复时当前精灵替代。
- `pet_progress`：各精灵稳定 ID、初始与当前成长分（首只初始 60，后续初始 0）、永久解锁时间与来源、满级事件、当前装配对象以及成长规则版本；满级阈值仍待设计。
- 建议保存装配切换事件及实际生效时间，以支持历史回溯；装配可以随时切换，以周结算时保存的精灵 ID 为历史计分归属。切换不重置总分，历史重算保留原接收对象。
- 无上限且指数增长的分数建议用十进制整数字符串导出，并用精确整数运算；不可因浮点数精度限制让长期计分或恢复发生误差。
- 验收需覆盖正负连续切换、零次、漏记、重复结算、历史修正、超过常用数字精度的分数，以及备份恢复后精灵状态一致。
- 已确认的时间与修正规则：Asia/Shanghai 周一至周日，首次使用的下一完整周启用计分；无记录周需确认后才结算。历史餐记录变更后按原周精灵归属重算后续分数，并保留已解锁精灵；导出须保留启用周、确认状态、原接收对象与永久解锁事件。
